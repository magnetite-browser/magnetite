# ADR-0005: Optional, self-hosted, zero-knowledge sync

- Status: accepted (2026-11-06); protocol v2 replaces the email/password v1
  of the same day before any release. Amended by ADR-0008: a public server
  at sync.magnetitebrowser.org next to self-hosting; and by ADR-0009:
  Postgres instead of SQLite.

## Context

Project rule: no mandatory account and nothing that depends on a hosted
service; sync, if any, is optional and can be self-hosted. The server is
written in Rust, open source like the browser, and zero knowledge. The sync
chain follows the design of
[Brave Sync v2](https://github.com/brave/brave-browser/wiki/Brave-Sync-v2).

v1 used email + password: the server stored the email (personal data) and an
argon2id hash of a password-derived key, which its operator could attack
offline for weak passwords.

## Decision

- `magnetite-sync` (server): a single binary (axum; SQLite at first, Postgres
  since ADR-0009), configured by
  environment variables. `magnetite-sync-proto`: the one implementation of the
  protocol and its cryptography, shared by client and server. Both live in
  their own repository, magnetite-browser/magnetite-sync (moved there
  2026-11-07, so self-hosters need nothing of the browser).
- **Sync chain**: the first device generates a 32-byte random
  seed, shown once as 24 BIP39 words; other devices join by entering them.
  HKDF-SHA256 derives an Ed25519 signing key, the encryption key and opaque
  collection ids from the seed. The chain's id on the server is the public
  key. No email, password or device names exist anywhere.
- **Signed requests**: `Authorization: Magnetite-Sig <pubkey>.<ms>.<sig>` over
  method, the server's host, path below `/v2`, time and SHA-256 of the body;
  ±5 minutes; strict verification, weak keys refused. The body's hash also
  travels as `Content-Digest`, so the server checks the signature before it
  reads an upload (and the body against the hash after). A replay can only
  repeat the identical request on the same server within that window, which
  the versioned writes turn into a harmless conflict (the server also
  refuses chains it deleted minutes ago).
- **Encryption**: XChaCha20-Poly1305, collection id and version bound as
  associated data; plaintext padded to a power of two (min 1 KiB) so sizes do
  not reveal small changes.
- **Data model**: opaque, versioned collections; optimistic `PUT` with
  `base_version`, 409 on conflict. Merge is whole-collection last writer wins.
  Versions only go up on a device: a write counts only when the server
  acknowledges the exact version it was encrypted for, and a server copy
  older than the newest version the device has seen is refused.
- **Transport**: `https://` only (plain `http://` for loopback addresses),
  no redirects, connect and request timeouts. Per-chain storage limits and a
  cap on chains protect the server's disk (the server's README).
- **Server data**: public key, day of creation and last activity, collection
  ids, versions, ciphertext. Chains unused for 400 days (configurable) are
  deleted. `DELETE /v2/chain` erases everything. No request or IP logging.

## Consequences

- The server holds no personal data in the GDPR sense beyond what a
  reverse proxy logs; a stolen database yields nothing useful and nothing to
  guess.
- Losing every device and the 24 words means losing the synced data; the UI
  must make people keep the words. There is no recovery by design.
- A malicious server cannot read, forge or roll back data on a device, but it
  can withhold updates, and a device that has just joined takes whatever
  authentic version the server offers first.
- The sync code is stored in a file created with mode 0600 in the data
  directory; the macOS keychain follows with signed builds.
